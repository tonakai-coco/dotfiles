# ADR-0001: Issue自動PRの対象範囲と変更量判定

- ステータス: Accepted（採用）
- 決定日: 2026-08-26
- 対象: GitHub ActionsによるIssue起点の自動Pull Request

## 背景

IssueからSakura AI Engineを呼び出して修正案を生成し、検証後にPull Requestを作成する仕組みでは、対象ファイルを複数指定できる必要がある。

従来の実装は、AIへ渡す対象パスを最大3件に制限していた。

この制限は安全性を保ちやすい一方で、同じ目的の変更が4件以上のファイルに分かれる場合に、Issueを不自然に分割することになる。

一方、対象パスの件数だけを無制限にすると、AIへ渡す完全なファイル内容、生成Artifact、Pull Request本文が過大になる可能性がある。

人が通常の開発速度で実装して1週間を超える、または40時間を超える変更は、1件の自動PRへまとめず、目的や受入条件を分割して依頼する方が保守しやすい。

## 決定

### 対象パスの件数

Issue本文の`## 対象パス`に指定するファイル数から、業務上の最大件数制限を外す。

対象パスは、リポジトリ内の既存トラッキング済み通常ファイルに限定する。

絶対パス、`..`を含むパス、重複パス、Symbolic Link、バイナリ、未追跡ファイルは引き続き拒否する。

### 技術上限

件数制限の代わりに、AIとRunnerを保護するため、入力と出力のサイズに上限を設ける。

| 対象 | 上限 |
| --- | ---: |
| 対象パス指定全体 | 64 KiB |
| 1ファイルのAI入力 | 128 KiB |
| AI入力ファイルの合計 | 512 KiB |
| 1ファイルのAI生成結果 | 256 KiB |
| AI生成結果の合計 | 512 KiB |

これらは人手工数の推定値ではない。

モデルのコンテキスト、Artifact、Runnerの処理量を一定範囲に収めるための技術上限である。

### 変更量の評価

AIが生成した完全なファイル内容を一時的に適用した後、Secretを持たない検証Jobで実際のGit差分を測定する。

変更行数は、追加行数と削除行数の合計とする。

```text
変更行数 = 追加行数 + 削除行数
```

変更領域は、対象パスのディレクトリ構造から数える。

ネストしたパスは先頭2階層を1つの領域とし、リポジトリ直下のファイルは`<root>`として扱う。

変更量は、次の3段階に分類する。

| 判定 | 条件のいずれか | 処理 |
| --- | --- | --- |
| 通常 | 変更行数400以下、変更ファイル数5以下、変更領域数2以下 | 通常の検証へ進む |
| 要確認 | 変更行数401以上、変更ファイル数6以上、変更領域数3以上 | 検証とdry-runを継続し、判定結果を通知する |
| 分割依頼 | 変更行数801以上、変更ファイル数11以上、変更領域数4以上、または1ファイルの変更行数401以上 | Issueへ分割依頼を通知し、検証と公開を停止する |

「要確認」と「分割依頼」の条件は、いずれか1つを満たした場合に適用する。

これらの数値は、40時間を直接測定した値ではない。

40時間を超える可能性のある変更を自動PRへ流さないための、初期の保守的な変更予算である。

### 工数の扱い

人が実装した場合の正確な工数を、差分だけから自動算出しない。

同じ行数でも、単純な設定変更と複数領域にまたがる設計変更では必要な調査、テスト、レビューが異なるためである。

AIによる工数見積もりを停止判定の根拠にしない。

AIの見積もりは補足情報にとどめ、停止判定は実測したGit差分と変更領域で行う。

## 処理の配置

対象パスの件数を撤廃しても、処理の安全性を次の場所で維持する。

- 入力Jobで、対象パスの安全性と入力ファイルのサイズを確認する。
- 生成Jobで、AIの応答を完全ファイル形式として検証し、生成ファイルのサイズを確認する。
- 検証Jobで、Artifactを適用して実差分を測定する。
- 分割依頼と判定結果は、ファイル内容を含めず、ファイル数、行数、領域数だけをIssueへ通知する。
- 分割依頼になった場合は、`make`による検証、branch作成、commit、push、Pull Request作成を行わない。
- 公開Jobでも実差分を再測定し、検証Jobと異なる結果になった場合に大きな変更を公開しない。
- 判定結果が`normal`または`review`以外の場合、後続Jobへ進まない。

## 検討した代替案

### 最大3件を維持する

採用しない。

同一目的の変更が複数の設定ファイルに分かれる場合に、対象パスの件数だけを理由として依頼を分割することになる。

### 対象パスと変更量を完全に無制限にする

採用しない。

完全ファイル形式を使う現在のAI連携では、入力コンテキスト、生成結果、Artifactが無制限になるためである。

### AIに40時間を超えるか判定させる

採用しない。

AIの工数見積もりは、Issueの書き方やモデルの推論に依存し、再実行した場合にも同じ値を保証できないためである。

## 影響

対象パスの件数を増やせるため、同一目的の複数ファイル変更を1つのIssueで扱いやすくなる。

生成後の実差分を基準にするため、対象パスが多くても変更が小さい依頼と、対象パスが少なくても1ファイルの変更が大きい依頼を区別できる。

変更量が大きい場合はAI呼び出し後に停止するため、Sakura AI Engineのリクエストを1回消費する可能性がある。

差分が大きい場合でも、40時間超と断定せず、変更予算を超えたため分割を依頼したと通知する。

## 再評価条件

次の条件で変更予算を見直す。

- 成功した自動PRまたは人手PRを10件から20件程度蓄積し、実際の人手工数と差分指標を比較できるようになった場合。
- 変更量が小さいのに分割依頼となる事例が続いた場合。
- 変更量が大きいのに自動PRへ通過する事例が見つかった場合。
- Sakura AI Engineのモデルやコンテキスト上限が変わった場合。
- 入力またはArtifactの技術上限に達する依頼が続いた場合。

`Makefile`、`.github/workflows/`、`.github/scripts/`などの高リスク領域に対して、変更量とは別に人手承認を必須にするかは、このADRでは決めない。

その判断が必要になった場合は、別のADRとして記録する。

## 実装状況

このADRに対応するローカル実装は、`codex/auto-pr-github-actions`ブランチに作成している。

変更量の測定と分類は、`.github/scripts/auto-pr-common.mjs`に集約している。

Workflowの分割依頼ゲートは、`.github/workflows/auto-pr.yml`に組み込んでいる。

対象パスの件数、サイズ予算、Git差分の測定、分割判定を含むNodeテスト18件が成功している。

コミット、push、GitHub Actions上のSecret登録、GitHub上のE2E実行は、この記録作成時点では行っていない。
