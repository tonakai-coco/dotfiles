# ADR 0004: 指摘は今回の不具合だけ残し、人の承認は別コメントにする

- ステータス: 採用（data-workflow-tools から同期）
- 日付: 2026-10-26

## 文脈

Impact Review は、PR の差分を OpenAI 互換 LLM に渡して要約とインライン指摘を投稿する。マージは止めない。指摘の座標だけを検証し、内容の正しさまでは見ていなかった。

運用では細かい指摘が push のたびに繰り返され、人が確認する量が増えていた。参照したのは Claude Code チームのレビュー方針（2026-10-15、[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)）である。そこでの要点は、スタイルや既存コードの指摘を投稿しないこと、再レビューを収束させること、人の注意をリスクの高い変更に使うことである。

このツールは PR のコードを実行しない。1 job は 10 分で、レビュー要求の既定待ち時間は 420 秒である。ボットの承認を人の承認の代わりにはしない。

## 決定

1. **残す指摘は、今回の変更で入った具体的な不具合だけにする。** スタイル、命名、整形、コメント、片付け、診断、変更前からある挙動、引用の無い推測は投稿しない。引用は追加行か削除行から 8 文字以上取る。変更されていない文脈行やファイル全文との一致では残さない。
2. **発見と検証を分ける。** 1 回目が候補を出し、2 回目が「今回の変更で入った不具合か」を判定する。判定が残すと言ったものだけを投稿する。検証は最大 90 秒とする。検証が失敗したときは nit と note を捨て、引用を通過した must と important だけを残す。`Finding.confirmed` の初期値は `False` とし、検証を通過した指摘だけを `True` にする。
3. **再レビューは収束させる。** 同じ head の再実行はラウンドを増やさず、前回の指摘を抑制しない。別 head では、同じパス・重大度・題名、または同じパス・行・重大度の指摘を再掲しない。2 回目以降の nit / note は、今回の差分の行にあるものだけ残す。前回指摘から 3 行以内の言い換えも捨てる。差分が取れないとき、nit / note は残さない。4 回目以降は、新しい行にある must と important だけを残す。差分が取れないときは、それらも残さず、実装方針の見直しを制限欄に書く。
4. **人の承認が必要かは、レビュー指摘とは別の Issue コメントにする。** このコメントはマージを止めない。必須チェックにもしない。`REQUEST_CHANGES` は出さない。
5. **承認の初期判定は厳しくする。** コード変更、must、important、ワークフロー、認証、秘密情報、差分の切り詰め、検証失敗、前回差分の取得失敗は「必要」とする。ルートの `auth.py` と `auth/` 配下も認証パスに含める。コードは指摘が残っていなくても人が承認する。文書や画像だけで、残った指摘も被覆の欠けも無いときだけ「不要」とする。

## 採用しなかったこと

- **指摘ゼロのコード変更を承認不要にすること。** レビューが見逃した不具合を、承認コメントが打ち消す。コードの承認不要は、revert やインシデントを測ってから緩める。
- **AI の指摘が開いている間マージを止めること。** 誤検知でマージが止まる。必須チェックへの登録は引き続き行わない。
- **複数モデルの投票や、PR 上でのテスト実行。** job の時間と、未信頼のコードを実行しない制約に合わない。検証は 1 回の追加要求にとどめる。
- **人の承認をこのツールが代行すること。** 判定コメントは人に見る場所を示すだけで、承認そのものではない。
